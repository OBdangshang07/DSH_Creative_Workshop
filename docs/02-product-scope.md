# 产品范围与原则

## 1. 产品定位

DSH Creative Workshop 是插件生态的发现与控制平面。它把分散的 GitHub 仓库、包版本、验证证据、社区反馈和本机 profile 状态组织成一套可查询、可解释、可回滚的工作流。

它不是新的 DSH runtime，也不是把任意 Git 仓库直接执行起来的“万能安装器”。

## 2. 核心用户

| 用户 | 主要任务 | 最怕发生的事 |
|---|---|---|
| 普通使用者 | 找到合适插件并一次装好 | 安装失败、污染配置、插件窃取数据 |
| 高级用户 | 比较版本、组合能力、管理多个 profile | 隐式冲突、升级破坏、无法回滚 |
| 插件作者 | 发布标准化元数据、获得反馈、维护兼容性 | 搜不到、评价与旧版本混在一起、误报风险 |
| 合集维护者 | 创建可复现的插件组合 | 依赖漂移、顺序不确定、合集无法复现 |
| 审核/安全维护者 | 处理报告、发布风险信号、撤销版本 | “收录”被误解为安全背书 |

## 3. 五项目标的非 UI 定义

### 3.1 “一键式”的极简交互逻辑

一键不是跳过风险，而是把机器可以决定的步骤自动化，把必须由用户决定的内容压缩成一次明确确认。

`InstallIntent → Resolve → Explain → Confirm → Apply → Verify → Commit/Rollback`

普通路径只需要：选择目标 profile、确认一次变更摘要、等待完成。以下情况才升级交互：

- 有生命周期构建脚本；
- 需要危险权限或新凭据；
- 存在 peer/version/row/service/slot 冲突；
- 插件未通过最低验证或来源不可锁定；
- 安装会修改多个 profile 或 agent preset。

### 3.2 视觉主导与信息标准化

展示必须来自结构化字段。卡片骨架、规格表键集与视觉系统见 [UI 设计项目规划](11-ui-design-plan.md)。每个插件版本至少有：

- 标识、作者、来源和不可变版本定位；
- 类型与运行平面；
- 解决的问题与适用对象；
- 预览资产及其来源；
- 支持的 DSH/Node/OS/架构；
- 权限、网络、凭据、文件和生命周期脚本；
- 依赖、冲突、替代与可选组合；
- 验证证据、最后测试时间和已知问题；
- 安装、升级、禁用、回滚和彻底卸载语义。

README 文本只能补充，不能代替这些标准字段。

### 3.3 社区驱动的动态评价体系

评价绑定到 `插件版本 + DSH 基线 + 环境`，而不是永远挂在插件名下。系统分别计算：

- 使用者体验信号；
- 兼容成功率；
- 维护健康度；
- 安全与权限风险；
- 证据可信度；
- 时间衰减后的综合发现分。

星级、评论、自动测试和安全报告独立保存，不合并成不可解释的单分数。

### 3.4 精准标签化与网状检索

标签不是自由文本云，而是分面本体：功能、运行平面、输入输出、集成对象、平台、权限、成熟度、成本和受众。自由标签可用于发现候选，但进入标准筛选前需映射到受控词汇。

网状检索覆盖关系：

- 依赖/被依赖；
- 提供/消费 Cordis service；
- 注册/占用 Client slot；
- 冲突/替代/增强；
- 属于合集/被合集包含；
- 同一作者/组织；
- 与某 DSH 基线验证通过。

### 3.5 依赖关系与合集直观化

底层先建立可解释图模型：节点和边都带来源与版本条件。安装前求解的不只是 npm 依赖，还包括：

- profile bundle 层序；
- Cordis entry id 覆盖；
- service provide/inject；
- Client slot 单席位冲突；
- settings namespace 与 route 冲突；
- agent preset 作用域；
- 平台与权限条件。

合集是一份可版本化、可锁定、可复现的声明，不是简单收藏夹。

## 4. 关键用户旅程

### 4.1 发现并安装

1. 用户按目标、平台、风险偏好和已装插件检索。
2. 系统返回符合当前 DSH 环境的版本，并解释为何匹配。
3. 用户选择安装；Companion 读取本机 profile 状态。
4. Resolver 生成确定性计划、权限差异和冲突说明。
5. 用户确认；执行器完成安装、重启/热应用与健康检查。
6. 成功后记录本机 receipt；失败时自动回滚并保留日志。

### 4.2 安装合集

1. 用户选择合集与目标 profile。
2. 系统锁定所有成员版本并展示总权限、总冲突和层序。
3. 若某成员已有兼容版本，复用它；若互斥则阻断并给出可选解。
4. 整个合集作为一个事务应用；验收失败则整体回滚。

### 4.3 发布插件

1. 作者绑定 GitHub 仓库并选择可安装包/子目录。
2. 系统读取 package、bundle patch 和 workshop manifest。
3. 静态验证生成问题清单；通过后进入候选目录。
4. 可复现构建和沙箱 smoke test 产生证据。
5. 作者发布新版本时生成独立版本页，不覆盖旧评价。

### 4.4 评价与报告

1. 已完成安装/运行验收的用户可提交结构化评价。
2. 客户端附带匿名化环境摘要和 receipt 签名，用户可审阅后发送。
3. 安全报告走私密通道；普通兼容问题公开。
4. 结论变更、版本撤回和作者修复都会更新动态信号。

## 5. 范围边界

### MVP 包含

- 公开 GitHub 与作者提交的目录采集；
- 标准化 manifest 与验证报告；
- 插件版本详情、复合搜索和依赖图 API；
- GitHub 登录、收藏、合集和结构化评价；
- 本机 Companion、profile 选择、安装预检、执行、验证和回滚；
- 管理员审核、下架、风险公告和作者申诉。

### MVP 不包含

- 私有企业插件市场；
- 付费、分成和许可证购买；
- 云端代管 DSH 实例；
- 自动授予凭据；
- 任意脚本的强安全沙箱保证；
- “AI 自动审计通过即安全”的承诺；
- UI 设计与实现。

## 6. 成功指标

| 指标 | MVP 目标 |
|---|---|
| 有标准化字段的可安装候选占比 | ≥ 80% 的精选目录 |
| 环境可求解的安装计划 | ≥ 95% 的已验证版本 |
| 安装失败后的自动回滚成功率 | ≥ 99% |
| 安装结果可归因率 | 100% 有 receipt 和阶段日志 |
| 搜索结果解释覆盖 | 100% 返回匹配/排除理由 |
| 评价版本绑定率 | 100% |
| 高风险安装的明确确认率 | 100% |

不使用总安装量作为唯一北极星指标。更重要的是：用户能否理解将发生什么、失败后能否恢复、社区信号能否追溯。
